# BrandSpace — Decision Register

> **الملخص التنفيذي بالعربية**
>
> هذا المستند هو **سجل القرارات** ومركز المراجعة لمالك المنتج. وهو مقسّم إلى أربعة أقسام واضحة:
>
> 1. **افتراضات معتمدة** — مأخوذة مباشرة من متطلبات المالك، لا تحتاج نقاشًا.
> 2. **قرارات موصى بها** — اختيارات تقنية اتخذها المهندس المعماري مع الأسباب والبدائل؛ تُطبَّق ما لم يعترض المالك.
> 3. **قرارات منتج غير محسومة** — تحتاج بحثًا أو تجربة أو معلومات إضافية قبل الحسم.
> 4. **قرارات تتطلب موافقة المالك قبل البدء** — **لا تبدأ المرحلة الأولى من التنفيذ قبل الإجابة عليها**.
>
> **الأهم:** القسم الرابع يحتوي على القرارات التي تحجب التنفيذ فعليًا — خصوصًا: مزودو الذكاء الاصطناعي، هيكل الخطط والأسعار،
> قيمة الرصيد وسياسته، مزود الدفع والأسواق المستهدفة، وأولوية منصات التواصل الاجتماعي.
> يُرجى مراجعة القسم الرابع أولًا.

## How to Use This Document

| Section                         | Meaning                                                  | Action needed                                    |
| ------------------------------- | -------------------------------------------------------- | ------------------------------------------------ |
| §1 Approved assumptions         | Stated in the owner's requirements; treated as settled   | None — correct me if any is wrong                |
| §2 Recommended decisions        | Engineering choices with reasoning and alternatives      | Accept, or amend; silence is taken as acceptance |
| §3 Unresolved product decisions | Genuinely open; needs research, data, or a business call | Answer when ready; does not block Phase 1        |
| §4 Requires owner approval      | **Blocks implementation**                                | Answer before Phase 1 begins                     |

Each entry has an ID (`A-`, `R-`, `U-`, `D-`) so it can be referenced in code reviews and commits.
When a decision is made, record the date and the choice here — this file is the project's memory.

## 1. Approved Assumptions

Taken directly from the product requirements. These are settled and shape everything else.

| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A-01 | BrandSpace is a **bilingual Arabic/English** platform; Arabic RTL is first-class, not a translation layer                                                                                                                                                                                           |
| A-02 | The platform is **multi-tenant**; every customer belongs to an isolated **Workspace**                                                                                                                                                                                                               |
| A-03 | There are **three architecturally separated interfaces**: public website, customer dashboard, and Platform Admin                                                                                                                                                                                    |
| A-04 | Platform Admin is for the BrandSpace owner and authorized internal staff only, with platform-level permissions and future 2FA (this design makes 2FA mandatory for Owner and Admin from Phase 2)                                                                                                    |

| A-08 | Configuration is **versioned** with validation, activation, rollback, change history, and audit logging                                                                                                                                                                                             |
| A-09 | Secrets are encrypted at rest, never exposed to frontend code, never in logs or responses, and readable only as masked metadata                                                                                                                                                                     |

## 2. Recommended Decisions

Engineering choices made in this phase. Each states the decision, the reasoning, the alternatives rejected,
and what it would cost to change later.

| ID   | Decision                                                                                                      | Reasoning                                                                                                                     | Rejected alternatives                                                                                            | Cost to reverse                   |
| ---- | ------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| R-01 | **Modular monolith + monorepo**                                                                               | Small team velocity, transactional integrity across billing/credits, single deploy; boundaries preserved for later extraction | Microservices from day one (operational overhead, distributed transactions); separate repos (version skew)       | Low — designed for extraction     |
| R-02 | **Shared database, shared schema, `workspaceId` + RLS**                                                       | Scales to self-serve sign-up; RLS gives defense in depth; enterprise-dedicated instances remain possible                      | Schema-per-tenant (migration cost explodes); database-per-tenant (operationally heavy)                           | High — change early or not at all |
| R-03 | **TypeScript everywhere** (Next.js, Node API, Node workers)                                                   | Shared types, schemas, and domain packages across web/api/worker                                                              | Polyglot backend (Go/Python) — doubles toolchain, loses type sharing                                             | High                              |
| R-04 | **PostgreSQL 16+** as the only primary datastore                                                              | Relational integrity for money, JSONB for config, RLS for isolation, pgvector for embeddings                                  | MySQL (no RLS), MongoDB (wrong for financial invariants)                                                         | High                              |
| R-05 | **Prisma** with a tenant-scoped client extension                                                              | Best-in-class TS ergonomics + migrations; scoping enforced by construction, not by memory                                     | Drizzle (better SQL control, thinner tooling), raw SQL (unacceptable human-error risk)                           | Medium                            |
| R-06 | **pgvector** for Brand Brain, not a dedicated vector DB                                                       | Embeddings inherit the same RLS tenant isolation; MVP volumes are small                                                       | Pinecone/Weaviate/Qdrant — second, weaker isolation boundary and another vendor                                  | Low — extractable later           |
| R-07 | **Redis + BullMQ** for queues, delayed jobs, locks, rate limits                                               | Delayed jobs are essential for scheduling; local-dev parity; no cloud lock-in                                                 | SQS/Cloud Tasks (lock-in), Temporal (heavier; revisit at Phase 6 for publishing sagas), pg-boss (fewer features) | Low                               |
| R-08 | **Database is the source of truth for schedules**; the queue is an accelerator, with a reconciliation sweeper | A Redis outage must cost punctuality, not correctness                                                                         | Queue-only scheduling                                                                                            | Low                               |
| R-09 | **S3-compatible object storage** behind a `StorageProvider` interface, pre-signed uploads, no public buckets  | Vendor-swappable; API never proxies bytes; security by construction                                                           | Direct SDK coupling; serving files from the app origin (XSS risk)                                                | Low                               |
| R-10 | **Zod** as the single schema language (HTTP, jobs, webhooks, config, AI output, env)                          | One definition reused front and back; config validation gets it for free                                                      | Separate validators per layer; JSON Schema (worse TS ergonomics)                                                 | Low                               |
| R-11 | **Auth.js** with two isolated realms + custom RBAC                                                            | Fast to build, covers OAuth/credentials; realm separation is ours, not the library's                                          | Custom auth from scratch (risk), a hosted IdP now (cost and lock-in before product-market fit)                   | Medium                            |
| R-12 | **2FA mandatory for Platform Owner and Platform Admin from Phase 2** (stronger than "future support")         | Admin compromise is catastrophic; TOTP is cheap to add now                                                                    | Optional 2FA at launch                                                                                           | Low                               |
| R-13 | **Vitest + Testcontainers + Playwright + k6**; isolation suite is blocking in CI                              | Real Postgres/Redis in tests is the only way to prove RLS behavior                                                            | Mocked database tests (would not prove isolation)                                                                | Low                               |
| R-14 | **OpenTelemetry**, vendor-neutral export                                                                      | Avoids observability vendor lock-in; consistent trace context across API and workers                                          | Vendor-specific agents                                                                                           | Low                               |
| R-15 | **Separate `apps/admin` deployment on a dedicated hostname**                                                  | Hard separation of session realm, permissions, and blast radius                                                               | Admin routes inside the dashboard                                                                                | Medium                            |
| R-16 | **Reserve → confirm → settle** credit model with an immutable ledger and a materialized balance               | The only design that satisfies "no charge on failure", "no double charge", and "never negative" under concurrency             | Charge-after-success (overspend under concurrency); charge-before (refund complexity)                            | High                              |
| R-17 | **FIFO-by-expiry credit consumption**                                                                         | Customers are never surprised by credits expiring that they could have used                                                   | LIFO; proportional consumption                                                                                   | Low                               |
| R-18 | **Downgrades take effect at period end; upgrades immediately**                                                | Avoids refund complexity and abrupt capability loss; standard SaaS expectation                                                | Immediate downgrade with proration                                                                               | Low                               |
| R-19 | **Hosted checkout and hosted billing portal**                                                                 | Keeps PCI scope minimal; card data never touches BrandSpace                                                                   | Custom payment forms (PCI burden)                                                                                | Low                               |
| R-20 | **Entitlements resolved from our own `Subscription`/`Plan`**, never directly from webhooks                    | A provider outage or spoofed event can never change access                                                                    | Provider as the entitlement source of truth                                                                      | Medium                            |
| R-21 | **Uncertain publish outcomes are verified, never blindly retried**                                            | The single most important rule for avoiding duplicate posts                                                                   | Retry on timeout                                                                                                 | Low                               |
| R-22 | **Copilot tool calls are authorized server-side per call**; the model's claims are ignored                    | Prevents prompt-injection privilege escalation                                                                                | Trusting the agent's plan                                                                                        | Low                               |
| R-23 | **Raw AI prompts and completions are not persisted by default**                                               | Privacy by default; audit-safe summaries suffice for support and billing                                                      | Full logging by default                                                                                          | Low                               |
| R-24 | **Mock adapters for AI and social are first-class and permanent**                                             | Enables the whole vertical slice, CI, and local dev without real credentials                                                  | Real providers first                                                                                             | Low                               |
| R-25 | **404, not 403, for cross-tenant access**, with identical shape and timing                                    | Prevents existence inference                                                                                                  | 403 (leaks existence)                                                                                            | Low                               |
| R-26 | **Cursor-based pagination** on all tenant data                                                                | Correctness under concurrent writes; no deep-offset cost                                                                      | Offset pagination                                                                                                | Low                               |
| R-27 | **Expand/contract migrations**, deploys always backward-compatible                                            | Zero-downtime deploys; safe rollback                                                                                          | Breaking migrations with downtime windows                                                                        | Low                               |
| R-28 | **Single region at MVP**, region selection deferred                                                           | Complexity and cost are not justified before demand exists                                                                    | Multi-region from day one                                                                                        | Medium                            |
| R-29 | **Agency support via both models** (many brands in one workspace, or one workspace per client)                | Different agencies want different isolation/billing shapes; the data model supports both with no extra machinery              | Forcing one model                                                                                                | Low                               |
| R-30 | **True impersonation is prohibited at MVP**; support acts as a labeled platform actor                         | Impersonation destroys audit clarity and is the most abusable feature in any SaaS admin                                       | "Log in as user"                                                                                                 | Low                               |
| R-31 | **Dual control on financial configuration** (pricing, credit costs): one actor drafts, another activates      | Prevents single-actor pricing mistakes and insider risk                                                                       | Single-actor activation                                                                                          | Low                               |
| R-32 | **Tailwind + Radix** for the design system                                                                    | Native RTL support via logical properties; accessible unstyled primitives                                                     | Component libraries with opinionated, hard-to-RTL styling                                                        | Medium                            |
