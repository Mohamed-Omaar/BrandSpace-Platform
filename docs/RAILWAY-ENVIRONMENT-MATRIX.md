# BrandSpace on Railway — Environment Variable Matrix

> **الملخص التنفيذي بالعربية**
>
> جدول مرجعي لكل متغير بيئي يحتاجه النشر على Railway: اسمه بالضبط، والخدمات التي تحتاجه، ومصدره، وهل هو سرّي، وشكله — **دون أي قيمة حقيقية**.
> المتغيرات مصنّفة إلى سبع فئات: ما تولّده Railway، والمراجع بين الخدمات، والأسرار التي ننشئها، وإعدادات المالك، وإعدادات المزوّدين الخارجيين (تخزين الملفات ورمز الخدمة الداخلي أصبحا مطلوبَين فعليًا)، وما هو للتطوير فقط، وما هو **ممنوع في الإنتاج**.

**No value in this document is real.** Every example shows a _format_, never a
secret. Read `docs/RAILWAY-DEPLOYMENT.md` first for the reasoning.

**Source of truth:** `packages/shared/src/env.ts` (the Zod schema and
`assertProductionSafety`), plus every direct `process.env` read in `apps/*/src`
and `packages/*/src`. This matrix was generated from those, not from memory. If
the two disagree, the code is right and this file is stale.

### The rules the parser actually enforces

From `assertProductionSafety`, when either `NODE_ENV=production` or
`APP_ENV=production`:

- **Every key domain a service is permitted needs its managed key.** The ARN, not
  the KEK. Absent → _"required in production for this service"_.
- **Every key domain a service is NOT permitted is refused in both forms** — the
  ARN and the KEK alike → _"must not be present in production for this service"_.
  Holding an unusable key is not harmless: it is a credential waiting for the day
  somebody wires it up.
- **The KEK is no longer required in production, and is not a fallback.** It may
  be present (the same blueprint builds staging, where it is what encrypts) and
  production never uses it: `createKeyProvider` prefers the ARN and throws rather
  than derive a local key when `NODE_ENV=production`.
- **The three ARNs must be distinct, and so must the three KEKs.** Pointing two
  variables at one CMK satisfies every other rule and collapses two blast radii
  into one.
- **A service with any key domain needs AWS credentials; a service with none must
  not have them.** Railway offers no instance role, so a key without credentials
  cannot be used at all — and would be discovered at the first save rather than
  at boot.
- `CUSTOMER_SESSION_SECRET` ≠ `PLATFORM_SESSION_SECRET`.
- `DATABASE_PLATFORM_URL` ≠ `DATABASE_URL` when both are set.
- **No placeholder.** Any variable whose name matches `/SECRET|KEK|PASSWORD|KEY/i`
  is rejected if its value contains `change-me`, `placeholder`, `example`,
  `devonly`, `localhost`, `replace_with`, `ci-only` or `test-only`. A value
  copied from `.env.example` fails at boot, not at the first sign-in.

### Which process holds which key

Not every service gets every key. This is the blast-radius design, deployed.

| Key domain      |  W  |  D  |  A  |  P  |  K  |
| --------------- | :-: | :-: | :-: | :-: | :-: |
| Platform secret |  —  |  —  | ✅  | ✅  |  —  |
| Social token    |  —  |  —  |  —  | ✅  | ✅  |
| Customer MFA    |  —  | ✅  |  —  | ✅  |  —  |

Each ✅ means **both** that domain's ARN and, outside production, its KEK. Each
`—` is enforced, not merely unset: the service refuses to start if it is given
that domain in either form.

The dashboard verifies a TOTP at sign-in and holds that domain alone — a login
request must not be able to unwrap a platform provider credential (F-07). The
worker unwraps customer social tokens when publishing and holds that one alone.
The Control Center manages provider credentials and holds the platform domain
alone. The API is the only service that legitimately serves all three, and is
the only one that holds all three.

**The IAM policy says the same thing.** Each service has its own IAM user,
allowed `kms:Encrypt` and `kms:Decrypt` on exactly the keys in its row and
nothing else, so the boundary survives a leaked credential rather than depending
on nobody having set the wrong variable.

### The https constraint is a deployment-order constraint

`PUBLIC_WEB_URL` and `PUBLIC_API_BASE_URL` default to `http://localhost:…` and
production refuses `http://`. The API and worker call
`validateStartupConfiguration()` at boot and **throw** in production.

So these must hold real https origins before the first production boot can
succeed — which is why domain generation moves to step 9 of the deployment
order, before any service is expected to start.

## E — External-provider configuration

Two categories are configured by the **deployment**, through the variables
below. Every other category is configured in the **Integrations Hub**, written
to the secret vault through the Secret Service and referenced by configuration —
those are not Railway variables at all, and `SECRET_VAULT_KEK` (class C) is what
makes that possible.

### E.1 Object storage — live, owner-supplied

Cloudflare R2, or any S3-compatible endpoint. `readS3Configuration()` in
`packages/storage/src/factory.ts` is the only reader; nothing above
`packages/storage` knows the vendor's name.

| Variable                    | Services | Secret  | Required | Production rule                                                                                                                         |
| --------------------------- | -------- | :-----: | :------: | --------------------------------------------------------------------------------------------------------------------------------------- |
| `STORAGE_ENDPOINT`          | D P K    | **yes** | **yes**  | The R2 **S3 API** origin. Contains the Cloudflare account id, so seal it.                                                               |
| `STORAGE_BUCKET`            | D P K    | **yes** | **yes**  | **Must differ between production and staging.**                                                                                         |
| `STORAGE_ACCESS_KEY_ID`     | D P K    | **yes** | **yes**  | An R2 API token scoped to this bucket. Never an account-wide token.                                                                     |
| `STORAGE_SECRET_ACCESS_KEY` | D P K    | **yes** | **yes**  | Cloudflare shows it once.                                                                                                               |
| `STORAGE_REGION`            | D P K    |   no    |    no    | R2 requires `auto`, which is the schema default. **Leave unset.**                                                                       |
| `STORAGE_FORCE_PATH_STYLE`  | D P K    |   no    |    no    | `true` only for gateways needing `host/bucket/key`, such as MinIO. Leave unset for R2 and AWS. Only the exact string `true` enables it. |

**All four required values or none.** In production an incomplete set makes
`createObjectStore()` throw, naming the missing variables; it never falls back to
the filesystem, `/tmp` or memory. `/health/ready` on the API reports the contract
as `object-storage`.

**Not on `admin` or `web`, deliberately.** The Control Center displays file
metadata and never moves bytes, and it already holds the platform database
identity and the secret vault key. The marketing site touches no customer data.

**Never `NEXT_PUBLIC_*`.** Next.js inlines only `NEXT_PUBLIC_*` into client
bundles; none of these carries that prefix, so no browser receives any part of
them (`CLAUDE.md` §2.3).

### E.2 Service-to-service — live, owner-supplied

| Variable                 | Services | Secret  | Required | Production rule                                                                                |
| ------------------------ | -------- | :-----: | :------: | ---------------------------------------------------------------------------------------------- |
| `INTERNAL_SERVICE_TOKEN` | D A P    | **yes** |  yes\*   | ≥ 32 characters, random. **Same value within an environment, different between environments.** |

\* Not required for the process to boot, but without it the dashboard cannot ask
the API to send customer email and `/v1/internal/email/deliver` answers 404 to
everybody. The API logs a named warning at boot in production when it is absent.

**It is not a provider credential.** It grants exactly one capability: ask for
one of six named templates to be sent. It cannot compose a message and cannot
read anything back. It exists because a signup or password-reset request carries
no session to forward, and because the alternative — giving the customer-facing
dashboard the PLATFORM key domain — would trade the platform's blast-radius
separation for a feature (F-07, deployment doc §16.3).

**Not on `worker`:** it sends through the notification pipeline, so the token
would be a capability nothing uses.

## H — Bootstrap-only, process-local

**Never added to a Railway service.** These exist for the duration of one
interactive command — the production Platform Owner bootstrap, `docs/
RAILWAY-DEPLOYMENT.md` §24 — and are gone when it exits. A variable stored on a
service is readable by everybody with project access for as long as nobody
thinks to remove it, which is precisely the wrong property for both of these.

| Variable                            | Purpose                                                                                                                                                                                                                                                                                         |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BOOTSTRAP_PLATFORM_OWNER_EMAIL`    | The real Platform Owner's address. **Required** by the bootstrap, and deliberately never hard-coded in source (CLAUDE.md §2.2). Nothing in the running product reads it. Passed inline: `BOOTSTRAP_PLATFORM_OWNER_EMAIL='…' pnpm bootstrap:production-owner`.                                   |
| `BOOTSTRAP_PLATFORM_OWNER_PASSWORD` | **Avoid.** The bootstrap prompts for the password at the terminal without echoing it, which is the only good answer. This escape hatch exists for a shell that genuinely cannot prompt; the command prints a warning every time it is used, telling the operator to remove it if it was stored. |

The bootstrap refuses outright unless `APP_ENV=production`, `NODE_ENV=production`,
`DATABASE_PLATFORM_URL` resolves to the `brandspace_platform` role, the vault can
seal (`SECRET_VAULT_KMS_KEY_ARN`, class C), and stdout **and** stdin are a real
TTY — the last because the one-time TOTP seed and recovery codes must never be
printed into a pipe, a log or a redirected file.

capability deliberately withheld, and adding one "just in case" widens a blast
radius for nothing.

### Per-environment uniqueness checklist

These must **differ** between production and staging. Railway keeps variables
per environment, but nothing stops an operator pasting the same value into both.
